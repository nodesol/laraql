# LaraQL attribute reference

All attributes live in `Nodesol\LaraQL\Attributes`. They are discovered on `*.php` classes inside `config('laraql.directories')` (default `app/Models` and `app/GraphQL`). The class name argument is filled in automatically by the scanner, so it is never passed by hand.

## `#[Model]`

Applied to a concrete Eloquent model. Constructor:

| Argument | Type | Default | Purpose |
| --- | --- | --- | --- |
| `class` | `string` | auto | The annotated class. |
| `operations` | `?array` | `[]` | Per operation arguments; keys `query`, `query_collection`, `create`, `update`, `delete`. |
| `directives` | `?array` | `[]` | Directives applied to every generated operation (`@guard`, `@model`, `@namespace`). |
| `type_override` | `?array` | `[]` | `field => 'Type @directive'` merged over detected type fields. |
| `input_override` | `?array` | `[]` | `field => 'Type @directive'` merged over detected input fields. |
| `authorize` | `bool` | `false` | `true` derives policy directives for all operations. |

Generated members for `class Article`:

| Member | GraphQL kind | Source |
| --- | --- | --- |
| `Article` | `type` | Table columns except `$hidden`, plus detected relation fields. |
| `ArticleInput` | `input` | Columns in `$fillable`. |
| `article` | query | `Str::snake($shortName)`, filters `['id: ID @eq']`, resolver `@find`. |
| `articles` | query | `Str::snake(Str::plural($shortName))`, filters `['where: _ @whereConditions(column: {})', 'first: Int! = 10', 'page: Int', 'orderBy: _ @orderBy']`, resolver `@paginate(defaultCount: 10)`. |
| `ArticlePaginator` | `type` | Generated by Lighthouse's `@paginate` (`data`, `paginatorInfo`). |
| `createArticle` | mutation | `input: ArticleInput! @spread`, resolver `@create`. |
| `updateArticle` | mutation | `id: ID!`, `input: ArticleInput! @spread`, resolver `@update`. |
| `deleteArticle` | mutation | `id: ID! @whereKey`, resolver `@delete`. |

Authorization mapping when `authorize: true`:

| Operation | Directive |
| --- | --- |
| `article` | `@canFind(ability: "view", find: "id")` |
| `articles` | `@canModel(ability: "viewAny")` |
| `createArticle` | `@canModel(ability: "create")` |
| `updateArticle` | `@canFind(ability: "update", find: "id")` |
| `deleteArticle` | `@canFind(ability: "delete", find: "id")` |

Notes:

- Type fields use `Schema::getColumns()` from the model's table, so column names must be real and the database must be reachable.
- `$hidden` columns are removed from the type; `$fillable` columns define the input. A column that is neither hidden nor fillable is queryable but not writable.
- Non-nullable columns are emitted with `!`.
- Relation fields come from public methods without arguments that return an Eloquent `Relation`. To-one relations use `@hasOne`, `@hasOneThrough`, `@belongsTo`, `@morphOne` or `@morphTo`; to-many relations use `@hasMany`, `@hasManyThrough`, `@belongsToMany`, `@morphMany` or `@morphToMany`, with the type written as `[Related]`.

## `#[Query]`

Constructor: `class`, `name` (default `Str::snake($shortName)`), `return_type` (default the class short name), `directives`, `filters` (default `['id: ID @eq']`), `filters_override` (default `[]`), `query` (default `'@find'`), `authorize` (default `null`).

Generated SDL:

```graphql
extend type Query {
    {name} ( {filters + filters_override} ): {return_type} {authorize} {query}
}
```

`filters` and `filters_override` are plain strings such as `'id: ID @eq'`, `'slug: String! @eq'` or `'where: _ @whereConditions(column: {})'`; they are joined with newlines inside the argument list. `query` holds the Lighthouse directive that resolves the field, for example `'@find'`, `'@paginate(defaultCount: 10)'` or `'@field(resolver: "Article@findBySlug")'`.

## `#[QueryCollection]`

Same shape as `#[Query]`, with collection defaults: `name` = `Str::snake(Str::plural($shortName))`, `return_type` = `[Type!]!`, `filters` = `['where: _ @whereConditions(column: {})', 'first: Int! = 10', 'page: Int', 'orderBy: _ @orderBy']`, `query` = `'@paginate(defaultCount: 10)'`.

Because `@paginate` is applied, Lighthouse rewrites the field to return `<UnderlyingType>Paginator` (with `data` and `paginatorInfo`) and adds the `first` and `page` arguments itself.

`order_by_relations: true` makes the default `orderBy` filter orderable by relation aggregates. It is opt in, because Lighthouse answers a `relations` argument with a generated clause type per field (e.g. `QueryArticlesOrderByRelationOrderByClause`) instead of the shared `OrderByClause`:

```php
#[QueryCollection(class: Article::class, name: 'articles', order_by_relations: true)]
```

Relations that are not `BelongsTo`/`HasOne`/`HasMany`/`BelongsToMany` (such as `MorphTo`) and relations whose related columns are all hidden are left out; a relation is listed as `{ relation: "comments", columns: [...] }`, or without `columns` when the related model hides everything.

## `#[Mutation]`

Constructor: `class`, `name` (required), `return_type` (default the class short name), `directives`, `inputs`, `query` (default `'@<name>'`), `authorize`.

Default inputs per name:

| `name` | Default `inputs` |
| --- | --- |
| `create` | `['input' => 'TypeInput! @spread']` |
| `update` | `['id' => 'ID!', 'input' => 'TypeInput! @spread']` |
| `delete` | `['id' => 'ID! @whereKey']` |
| anything else | `['id' => 'ID!']` |

The generated field name is `{name}{ShortName}`, for example `createArticle`.

`authorize: true` maps to `@canModel(ability: "create")` for `create` and `@canFind(ability: "<name>", find: "id")` for everything else.

## `#[Type]`

Constructor: `class`, `create_paginator` (`false`), `name` (default the class short name), `columns` (`null`), `columns_override` (`null`), `extends` (`null`).

- Without `columns`, the type is built from the class properties: typed properties use their type, untyped properties default to `String!`, non-nullable properties get `!`, and class types are referenced by their short name.
- `columns` replaces that detection (`['id' => 'ID!', 'title' => 'String']`), `columns_override` merges on top of whichever list is used.
- `create_paginator: true` also emits `<Name>Paginator` wired to Lighthouse's paginator field resolvers, for fields resolved with `@field(...)` instead of `@paginate`.
- `extends: 'Node'` writes `type Name extends Node`.

## `#[Input]`

Constructor: `class`, `name` (default `ShortName.'Input'`), `inputs` (`null`), `inputs_override` (`null`).

- Without `inputs`, the input is built from the class properties using the same rules as `#[Type]`.
- `inputs` replaces the detection and `inputs_override` merges on top of it.
- Values are `Type` or `Type @directive`, for example `'title' => 'String! @rules(apply: ["required"])'`.

## Column type mapping

`Nodesol\LaraQL\Types\ColumnTypes::getType()` matches the database type name reported by `Schema::getColumns()` in this order, so the first matching group wins:

| Order | Database type names | GraphQL type |
| --- | --- | --- |
| 1 | `smallint`, `mediumint`, `int`, `integer`, `bigint`, `year`, `binary` | `Int`, or `ID` when the column is auto-increment |
| 2 | `tinytext`, `text`, `mediumtext`, `tinyblob`, `blob`, `mediumblob`, `json`, `string`, `ascii_string`, `array`, `varchar`, `enum` | `String` |
| 3 | `boolean`, `tinyint` | `Boolean` |
| 4 | `float`, `decimal` | `Float` |
| 5 | `json`, `object` | `Json` |
| 6 | `date` | `Date` |
| 7 | `datetimetz` | `DateTimeTz` |
| 8 | other datetime types and `timestamp` | `DateTime` |
| 9 | anything else | `String` |

Two consequences worth remembering:

- Because `json` already matches the string group, a JSON column becomes `String`; only an `object` column reaches `Json`. Override with `type_override` when the API should expose structured JSON.
- The type names come from the database driver, so the same Laravel column definition can report different names on MySQL, PostgreSQL or SQLite. Always confirm with `lighthouse:print-schema` instead of guessing.

Non-nullable columns get `!` appended. If a mapped type is not one LaraQL ships (`Upload`, `DateTime`, `Date`), define that scalar in the Lighthouse schema file or override the field.

## Relation type mapping

`Nodesol\LaraQL\Types\RelationTypes` lists the Eloquent relation classes LaraQL recognizes:

- Single value (type `Related`): `HasOne`, `HasOneThrough`, `BelongsTo`, `MorphOne`, `MorphTo`.
- Multiple values (type `[Related]`): `HasMany`, `HasManyThrough`, `BelongsToMany`, `MorphMany`, `MorphToMany`.

## Directives LaraQL adds on its own

Besides the Lighthouse directives referenced by the generated SDL, LaraQL appends these definitions to every schema:

- `scalar Upload`, `scalar DateTime`, `scalar Date`.
- `extend type Query { graphql(id: ID): [String!] @find }` - a utility field used by the package's own tooling.
- `directive @whereConditions(...)` and `directive @whereHasConditions(...)`, matching Lighthouse's where conditions API with a default handler.

The Scout integration adds `directive @scoutFilters`, the `ScoutFilters` input, `ScoutFiltersCondition`, the `MeilisearchOperator` enum and `scalar Mixed`. See the `laraql-scout-search` skill.
